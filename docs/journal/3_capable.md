## Where the program stands now.

### High level architecture diagram
- Everything hangs off the MUD socket session - the same connection gets shared by the raw move/attack tools, navigate_to, explore, and combat_loop so they're not fighting each other for control.
- Room memory is split into a few pieces: RoomParser turns raw text into structured data, RoomMemory hashes and stores it per room, and WorldGraph is the actual map (a directed graph of rooms connected by exits).
- Added a whole exploration layer on top of that - BlockedExits remembers locked doors/dark rooms so it stops retrying them, and there's now dark-room detection so it doesn't wander in blind.
- Combat got its own safety layer too - it won't attack something that isn't actually in the room, and it won't attack something it's going to lose to, unless I force it.
- The dashboard is just a Flask app reading the same memory files everything else writes to - map, overview, live feed, goals, sessions, all pulling from the same source of truth.
- Watched a live play session with Claude Code this week and found two real bugs in that combat/exploration layer, not just bad LLM judgment: RoomParser was filing any mob with a long custom description as an "item" instead of an "npc," which silently made it unattackable - and explore()'s frontier search is global across the whole map, so once the nearby area's fully mapped it'll happily walk you all the way back to town for some leftover unexplored exit there instead of pushing further into a dungeon. Fixed the parser's default and gave explore() an optional max_hops so it can be told to stay local.
- Added map enrichment and smarter navigation resolution. `memory/map_enrichment.py` enriches the dashboard's Map tab with visual zone groupings (rooms clustered by proximity into colored areas), edge classification (walked vs inferred vs frontier), and per-room chips showing aliases and unwalked exit counts. On the navigation side, when deterministic path matching fails or produces the wrong room (both observed live — "bakery" finding nothing, "guild" matching the wrong guild), the agent now falls back to an LLM-assisted resolver that uses its own memory of what it has seen to pick the right destination. Learned aliases (`RoomAliases`) let the agent permanently register short names for rooms so the LLM fallback is only needed once per destination.
- Added equipment tracking. Two new pure parsers (same "no LLM" shape as RoomParser/PlayerStats) turn `check equipment` and `identify` spell/scroll output into structured data - what's worn in every slot, and what AC/hitroll/damroll/stat bonuses an identified item actually has. Reused the existing cast_spell/use_magic_item tools for identify instead of adding a new one. Loadout gets stored per character; identified item stats get stored world-scoped (shared across characters, like the knowledge file) since an item's stats aren't tied to who's wearing it.
- The interesting part was a bug that only showed up once everything was wired together: the equipment-listing parser and the identify-output parser each invented their own names for the same wear slots (one said "worn around neck," the other said "neck"), so the upgrade advisory silently never fired for most slots even though every individual piece had its own passing tests. Had to build one shared slot-name table both parsers go through. Good reminder that testing pieces in isolation doesn't catch this kind - needed an end-to-end test that actually pipes one parser's output into the other's input.
- Money now has somewhere real to go. `GoldMonitor` sits next to `CombatMonitor` and does the same kind of job - checks carried gold against a threshold in the goal file (200 by default, same pattern as `hp_flee_threshold`) and tacks a note onto the score check telling the agent to bank half once it's over. `bank()` itself got smarter too - deposit/withdraw don't tell you your new balance, so it now automatically follows up with a balance check and saves that number (`bank_gold`) the same place hp/gold/level already live. Dashboard shows both numbers side by side now.
- Combat and looting got a couple of real fixes instead of just LLM judgment calls. `attack()` used to leave the agent stuck repeating "You're fighting the best you can!" forever because the code drains any buffered text right before sending a command, which was throwing away the actual combat output the MUD pushes on its own mid-fight - now it just tells the agent to switch to `combat_loop()`, which doesn't drain between rounds. Separately, `RoomParser` was only recognizing a monster line if it ended in a period, so any monster whose flavor text ends in "!" or "?" was silently invisible to the attack tools even though `look` showed it fine - widened that check.
- `get_item` had a syntax bug that only showed up on multi-word item names with a count attached - it was sending something like "get 1 shiny newbie dagger" which isn't valid syntax for this MUD, and the server would misfire onto some unrelated item instead of the one being requested. Fixed to only send a number when actually asking for more than one.
- Added a `read` tool, separate from look/examine, since this MUD treats reading a sign/note/board as its own verb and there was no way to act on all the "you probably should read this" text sitting in room descriptions.
- Added an Inventory tab to the dashboard - equipped items and carried (unequipped) items side by side, per character. `check(kind="inventory")` already existed as a tool the agent could call, but its result was only ever handed back to the LLM and discarded, unlike `score` and `equipment`, which both already flowed into `players.json`. Added a `parse_inventory` parser (same shape as `parse_equipment`), a `PlayerTracker.update_inventory` method, and one new branch in `_check_and_record` so an inventory check now persists the same way a score or equipment check already did. No new API route needed - `/api/players` and `/api/overview` already pass the whole per-player record through, so the new `inventory` field just showed up once something started writing it.
- Found (via a live-session death investigation, not code review) that `combat_loop`'s per-round HP-based auto-flee has never actually worked on this server. `combat.py`'s HP regex expects a "current/max" format like `45/93H` inside each combat round's text, but this MUD's real in-combat prompt is `45H 100M 89V` - bare current values, space-separated, no slash, no max number. Checked the full session transcript: zero combat rounds all session ever matched the slash-format regex, meaning `_parse_hp()` always returned `None` mid-fight and the flee-on-low-HP check (`CombatMonitor.update_on_low_hp`) never had a chance to fire, regardless of what `flee_hp` was set to. The character's only remaining protection was the pre-fight `consider` danger check and the "quiet rounds" detector for a fight that's gone silent - neither one catches a nominally fair fight that just goes badly over many rounds, which is exactly what happened both times the character died. The existing unit tests for `combat_loop` didn't catch this either, because their mocked round text used the same wrong `34/37H` slash format the code expects - the whole test suite was internally consistent with a prompt format the live server doesn't actually use.
- `equip_item`'s `body_loc` parameter is now permanently ignored when building the MUD command (still accepted in the schema, just never sent) - grepped session logs going back to the first sessions in early August and never found one case where a model-supplied `body_loc` actually helped. Every single recorded use was the model echoing an item's own slot name back ("torso", "sleeves", "legs") and getting a hard rejection from the server. `wear`/`wield`/`hold`/`grab`/`remove` all auto-infer the slot from the item on this server, so the parameter was pure downside.
- `get_item`, `drop_item`, `put_item`, and `give_item` now all run their `count` argument through a new `_normalize_count()` helper before touching it - coerces to `int` or drops it to `None` on anything unparseable (a stray `count=""` or `count="1"` string from the model, which happens in practice). Needed because tightening the `count != 1` check to `count > 1` (to also stop a bogus `count=0` from desyncing the MUD's parser) introduced a `TypeError` the first time the model sent count as a string instead of an int - a straight-up regression caught live, same session, by watching the monitor output.
- `move()` now appends a one-line hint - "try door(action='open', ...)" - whenever the MUD's response contains "seems to be closed," instead of just returning the raw rejection and letting the model rediscover the same fix by trial and error every session.
- Confirmed, not fixed, that `RoomParser` deliberately defaults ambiguous long-description lines to `npcs` rather than `items` (see the comment at `memory/parser.py:85-100`) - a real tradeoff, not a bug: a static item misfiled as an npc only costs a harmless rejected `consider`, but a real mob misfiled as an item becomes permanently unattackable. Shows up live as things like a ground-item helm listed under "NPCs:" in `process_room` output. Agent just needs to try `consider`/`attack` first and fall back to `get_item` once it's confirmed nothing's living there.
- New world-knowledge facts written this session (same `.boukensha/knowledge.yaml` file, auto-injected every session): that item names only match on a single trailing-noun keyword rather than the full descriptive string, and the real CircleMUD mechanic for identifying magic drops (`cast 'detect magic'` for aura-only, `cast 'identify'` or a scroll for full stats, sage/shop fallback if the class can't cast). Both came from watching the same "tries the full name three times, gives up, asks me what to do" failure pattern live.
- Confirmed a real limitation in the auto-continue loop: it resumes with a fixed `"continue toward the current goal"` directive that doesn't force a fresh `goal_read`, so editing `.boukensha/goals/current.yaml` while a session is mid-run has no effect until the process is restarted (or the model happens to call `goal_read` again on its own). A code fix or a goal change both need a restart to actually take effect on an already-running session.

### Data Flow
- User (me) gives it a goal -> agent loop decides which tool to call -> tool talks to the MUD -> result gets parsed and saved to memory before it ever goes back to the LLM.
- Most of the "thinking" now happens in code, not the LLM - process_room only sends back what's new, navigate_to/explore just run the pathfinding and walk it themselves.
- Every room it parses updates three things at once - room memory, the world graph, and now a "who's actually alive here" list the combat tools check against - and that npc/item split is exactly what the RoomParser bug above was corrupting.
- If a planned route doesn't match reality (wrong room, blocked move) it stops immediately and fixes the map instead of blindly continuing - that was a big source of the "confused" behavior earlier.
- All of this gets logged to JSONL as it happens, which is what feeds the live tab, waterfall, and sessions viewer in the dashboard - sessions viewer now shows the list and transcript side by side instead of stacked, so clicking a session doesn't mean scrolling past hundreds of rows to see it.
- Also caught a REPL bug where typing "continue" to resume a session was overwriting the actual goal text with the literal word "continue" - fixed so a resume phrase just reactivates the existing goal instead of replacing it.
- Equipment now flows through the same "parse -> save -> only bother the LLM if something's actionable" pattern as everything else: checking equipment or identifying an item updates memory silently, and the agent only sees a message ("[Equipment] this ring beats what's in your finger slot") when there's actually a decision worth making - it still has to decide whether to wear it, nothing gets auto-equipped for it.
- Gold now flows through that same pattern too - score check parses gold, compares to the threshold, and only says something ("[Bank] you're over 200, go deposit half") when it's actually worth acting on. Same idea as the equipment upgrade advisory and the level-up/sustenance ones - code does the noticing, LLM only gets pulled in when there's a real decision to make.
- Learned the hard way (a couple of times now) that guessing at what the MUD's response text looks like instead of checking a real transcript is how bugs sneak into tests and stick around - the bank balance regex was built off a guessed format that didn't match the real server reply, and it took watching a live run to catch it. Same root cause as the RoomParser period-only bug. Going forward I want to push for "check the real transcript first" before writing any parser or regex against MUD output.
